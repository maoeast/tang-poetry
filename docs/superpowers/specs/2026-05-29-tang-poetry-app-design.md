# 唐诗画境一期设计规格

**目标：** 构建一个面向中文学习者的全栈 Web 应用，将唐诗学习、儿童绘本水彩图像、AI 讲解、挑战闯关与复习成长整合为统一体验。

**产品定位：** 这不是单纯的诗词题库，而是一个“可学、可玩、可沉浸、可积累”的唐诗学习产品。一期聚焦 `儿童绘本水彩` 主视觉、完整学习闭环和可持续扩展的数据与系统边界。

**当前日期：** 2026-05-29

---

## 1. 背景与问题

当前项目内已有两个可借鉴的 skill：

- [`SKILL.md`](../../../SKILL.md)：强调对句挑战、评分、错题分析。
- [`poem/SKILL.md`](../../../poem/SKILL.md)：强调每日一诗、验收、复习池、诗人缘分。

当前本地数据源 [`references/tang_poetry.json`](../../../references/tang_poetry.json) 只有 100 首，覆盖面和玩法支撑力有限。用户进一步确认将采用 GitHub 仓库中的 [`唐诗三百首.json`](https://github.com/chinese-poetry/chinese-poetry/blob/909646524737b70544ee7ae17cb76868a0bc8a55/%E5%85%A8%E5%94%90%E8%AF%97/%E5%94%90%E8%AF%97%E4%B8%89%E7%99%BE%E9%A6%96.json) 作为主数据来源。

同时，用户希望为诗歌生成配图，并已提供 3 张参考图，整体视觉方向明确为：

- 儿童绘本水彩
- 柔和国风
- 四周包裹式构图
- 中央留白排版
- 画面辅助记忆，而不是纯装饰

项目运行约束也已经明确：

- 本地开发环境：Windows 10 和 Deepin 25 双系统
- 生产环境：腾讯云轻量服务器（2 核 4 G，SSD 70 GB，Ubuntu）
- 代码托管：GitHub
- 首期访问方式：HTTP + 公网 IP，无域名，暂不配置 HTTPS

## 2. 一期目标

一期目标不是做完所有内容，而是交付一个可以长期演进的完整产品骨架。

一期必须完成：

- 完整前后端应用，而不是单页演示。
- 统一诗歌主数据模型。
- `今日一诗` 学习入口。
- `诗歌详情` 沉浸阅读页。
- `对句挑战` 基础闯关玩法。
- `复习池` 与用户学习记录联动。
- `AI 讲解` 能针对单首诗生成解释与延展。
- `我的成长` 页面，展示连续学习、收藏与诗人缘分。
- 儿童绘本水彩主视觉落地。
- 图片策略采用 `核心预生成 + 长尾后补`。

一期不强求完成：

- 300 首全部精修场景图
- 多风格主题切换
- 音频朗读与跟读评分
- 社交排行
- 分享海报生成
- 教师端或班级端
- 完整多用户体系

## 3. 用户与核心场景

### 3.1 目标用户

- 小学生及其家长
- 诗词启蒙用户
- 希望通过图像记忆学习诗词的用户
- 喜欢国风审美的中文学习者

### 3.2 核心使用场景

1. 用户打开应用，看到 `今日一诗`，被一张诗意配图吸引，阅读主句与讲解。
2. 用户进入诗歌详情页，查看全文、拼音、译文、主题图与 AI 讲解。
3. 用户进入挑战页，通过上句对下句、作者判断、诗名选择和乱序排句等方式练习记忆。
4. 用户在复习页练习自己学过或答错的内容。
5. 用户在“我的”页面看到学习天数、点亮诗作数和最有缘的诗人。

## 4. 视觉方向

### 4.1 一期主风格

一期仅支持 `儿童绘本水彩`。

关键词：

- 柔光
- 温暖
- 低饱和
- 国风自然元素
- 留白
- 亲和
- 适合儿童阅读

### 4.2 配色原则

- 春景：嫩绿、浅粉、暖黄
- 夜景：雾蓝、月白、淡灰紫
- 山水：青绿、石青、远山蓝
- 边塞：赭石、沙金、暮红
- 思乡：月白、灰蓝、米杏

### 4.3 构图原则

- 场景图与文字分离。
- 图片中央或偏中留出安全排版区域。
- 四周由枝叶、窗景、山水、人物或物件进行包裹。
- 避免在图片中写死诗文正文。

### 4.4 二期预留

二期新增 `雅致工笔国风` 风格，作为用户可切换主题。为避免未来返工，一期的图片索引、页面主题系统与样式变量都必须预留多主题扩展能力。

## 5. 数据策略

### 5.1 主数据源

采用 GitHub 仓库中的 `唐诗三百首.json` 作为主数据源。该文件当前包含 366 条记录，字段结构为：

- `id`
- `title`
- `author`
- `paragraphs`
- `tags`

### 5.2 数据清洗原则

导入后生成统一格式，示例：

```json
{
  "id": "ts300-0001",
  "sourceId": 1,
  "title": "在岳咏蝉",
  "titleOriginal": "在嶽詠蟬",
  "author": "骆宾王",
  "authorOriginal": "駱賓王",
  "dynasty": "唐",
  "lines": [
    "西陆蝉声唱，南冠客思侵。",
    "那堪玄鬓影，来对白头吟。",
    "露重飞难进，风多响易沉。",
    "无人信高洁，谁为表予心。"
  ],
  "tags": [],
  "themes": [
    "咏物",
    "自况"
  ],
  "difficulty": 2,
  "imageKey": "ts300-0001",
  "imageStatus": "placeholder"
}
```

### 5.3 清洗要求

- 保留原文与展示用简体字段。
- 将 `paragraphs` 转为 `lines`。
- 繁简转换统一使用 `opencc-js`。
- 补充统一 `dynasty` 字段。
- 生成稳定的内部主键。
- 预留 `themes`、`difficulty`、`imageKey`、`imageStatus` 字段。
- 允许后续人工补录 `annotation`、`translation`、`pinyin`、`notes`。

### 5.4 今日一诗排期

不使用日期哈希算法。改为单独维护 `DailyPoetry` 数据表：

- `date`：字符串，格式为 `YYYY-MM-DD`
- `poetryId`

导入脚本负责提前生成未来一年每日诗歌映射，并批量写入数据库。节气、节日等特殊日期可以后续手工调整。

## 6. 图片策略

### 6.1 总体策略

采用 `核心预生成 + 长尾后补`。

### 6.2 一期范围

- 先为 30 到 50 首高频名篇制作高质量主图。
- 其余诗作先使用统一风格的占位图卡。
- 所有诗作都具备图片槽位与索引结构。

### 6.3 资产分层

每首诗的视觉资产分为两层：

1. `场景主图`
2. `HTML 动态排版`

场景主图只负责意境和记忆点，不包含写死的诗文段落；正文、拼音、作者、标题、译文全部由页面渲染。

### 6.4 运行时数据源

图片资产以数据库中的 `ImageAsset` 表作为唯一运行时数据源。`image-assets.json` 仅作为批量导入脚本的中间产物，不参与运行时读取。

运行时图片查询规则：

- 优先返回数据库中 `status = "ready"` 的资产
- 缺失时回退到占位图
- 回退逻辑不依赖 JSON 文件

### 6.5 图片使用场景

- 首页 `今日一诗` 主视觉
- 诗歌详情页头图
- 挑战页背景卡
- 收藏列表封面
- 分享海报的背景底图

## 7. AI 能力边界

### 7.1 DeepSeek 的职责

DeepSeek 负责：

- 诗句讲解
- 意境白话解释
- 面向儿童的表述转换
- 延展提问
- 鼓励式反馈
- 基于主题的相关推荐文案

### 7.2 DeepSeek 不负责

DeepSeek 不负责：

- 标准答案判定
- 对句校验的最终裁决
- 题库抽样逻辑
- 用户进度规则计算

这些能力应由本地规则、结构化数据和后端逻辑完成，以保证稳定性与一致性。

### 7.3 AI 讲解缓存

`Poetry` 表新增 `aiExplanation Json?` 字段，用于缓存不同受众与不同 prompt 版本的讲解结果。

缓存结构示例：

```json
{
  "child_v1": {
    "summary": "这首诗写的是……",
    "imagery": "你可以把它想成……",
    "emotion": "诗人当时……",
    "cachedAt": "2026-05-29T10:00:00Z"
  },
  "general_v1": {
    "summary": "……",
    "imagery": "……",
    "emotion": "……",
    "cachedAt": "2026-05-29T10:00:00Z"
  }
}
```

约束如下：

- key 格式为 `{audience}_{promptVersion}`
- 一期 `audience` 仅支持 `child` 与 `general`
- `promptVersion` 从 `v1` 开始
- prompt 升级时仅提升版本号，旧缓存保留

服务端讲解路由逻辑：

1. 按 `poetryId + audience + promptVersion` 查询缓存 key
2. 命中则直接返回，不调用 DeepSeek
3. 未命中则调用 DeepSeek，写回对应 key 后再返回

## 9. 关键业务规则

### 9.1 今日一诗

- 同一自然日固定同一首诗。
- 不支持“重新抽一首”。
- 今日诗由 `DailyPoetry` 排期表决定。
- 今日诗应优先从高质量图像池中选取。
- 若当天命中的诗没有精修图，则回退到占位图。

### 9.2 挑战判题

- 对句判题以清洗后的标准诗句为准。
- 比较时忽略常见中文标点与首尾空格。
- `ordering` 题型出题时，若随机结果与原始顺序一致，必须重新随机。
- AI 不参与最终是否正确的判定。

### 9.3 复习来源

- 优先来自用户已浏览、已完成挑战或答错的诗。
- 不做完全随机全库抽题。
- 错题与低熟练度内容优先。

### 9.4 复习调度

一期采用写死参数的固定规则，不做模糊“智能估算”：

| 事件 | 规则 |
|------|------|
| 首次学习后 | 加入复习池，`nextReviewAt = 当天 + 1 天` |
| 答对一次 | 间隔按序列推进：`1 → 2 → 4 → 7 → 15 → 30` 天，30 天封顶 |
| 答错一次 | `wrongCount + 1`，`nextReviewAt = 次日`，`mastery - 1`，最低为 0 |
| 连续答错 3 次 | `nextReviewAt = 当天`，进入今日强制复习 |

### 9.5 诗人缘分

根据用户最近一段时间学习记录统计作者出现次数，生成“最有缘诗人”排序。

## 10. 技术架构

### 10.1 一期推荐技术栈

- 前端：Next.js + TypeScript + React
- 样式：Tailwind CSS
- 数据库：Prisma + PostgreSQL 16
- 本地数据库启动：项目根目录 `docker-compose.yml`
- 服务端：Next.js Route Handlers
- AI 代理：服务端封装 DeepSeek 请求
- 繁简转换：`opencc-js`
- 图片资源：本地静态目录 + 数据库索引

### 10.2 选择理由

- 统一前后端仓库，适合从零启动。
- 前后端统一使用 PostgreSQL，避免本地和线上数据库差异。
- 既能输出 HTML 页面，也方便接入 API、数据库与中间件访问保护。
- 便于后续扩展主题、用户体系和部署。

### 10.3 一期访问保护

一期不实现注册登录系统，而采用单用户访问保护：

- 通过环境变量 `APP_PASSWORD` 提供访问口令
- 通过 Next.js middleware 验证并写入 cookie
- 数据模型仍保留 `userId` 维度，但一期固定使用 `SYSTEM_USER_ID`

这必须明确标注为：

- 一期单用户实现
- 不是系统永久不支持多用户

### 10.4 访问保护的安全说明

一期访问保护方案（`APP_PASSWORD + cookie + HTTP`）是在以下条件下有意识做出的权衡：

- 应用为家庭私有部署，无支付、无敏感个人数据
- 无域名阶段无法配置 HTTPS 证书
- 实际威胁模型风险极低

但文档必须同时记录：

- 公网 HTTP 下密码与 cookie 不具备传输加密
- 该方案仅适用于当前低风险私有场景

后续升级路径：

- 购买域名并完成备案后，使用 Certbot 为 Nginx 配置 Let's Encrypt 免费证书
- 启用 HTTPS 后，将 cookie 标记为 `Secure + HttpOnly + SameSite=Strict`
- 届时 `APP_PASSWORD` 方案才具备真正的传输安全性

## 12. 非功能要求

- 页面首屏需在普通桌面浏览器与手机端都可正常阅读。
- 图片与文字叠加时必须确保对比度与可读性。
- AI 接口失败时页面仍可展示本地诗歌基础内容。
- 所有核心功能应允许无图或占位图降级运行。
- 后端与前端边界要清晰，避免后续风格扩展时牵动业务逻辑。
- 文档中的路径一律使用相对路径，不出现盘符和绝对路径。
- 项目根目录必须补齐 `.gitattributes`、`.nvmrc`、`docker-compose.yml`、`.env.example`。

## 13. 一期验收标准

满足以下条件视为一期骨架可用：

- 应用可启动并浏览首页、详情页、挑战页、复习页、我的页面。
- 已成功导入并展示完整诗歌主数据。
- `DailyPoetry` 表中已写入未来一年的每日排期。
- 至少 30 首诗具备精修主图索引。
- 对句挑战与乱序排句可正常出题、判题、反馈。
- 用户学习记录可写入并影响复习与缘分榜。
- AI 讲解可通过服务端代理生成、缓存并展示。
- 页面在移动端和桌面端均具备完整可用体验。

## 14. 风险与约束

- GitHub 数据存在简繁、异体字与标题差异，需要清洗映射。
- 300 首配图若一次性全量制作，成本高且不利于快速交付。
- 若将诗文写死进图片，会严重降低后期可维护性，因此必须坚持图文分离。
- DeepSeek 若直接放在前端会暴露密钥，因此必须走服务端代理。
- 公网 HTTP 下的密码访问方案不具备传输加密，只适合当前低风险场景。
