# 单一配置源 + 闭环会话交接：写好 AGENTS.md / CLAUDE.md 与会话交接的实战经验

## 引言：代理协作的两个头号摩擦

同时用 Codex 和 Claude Code 的人，最常踩两个坑：

1. **双份维护**——`AGENTS.md` 和 `CLAUDE.md` 内容几乎一样，改一处忘另一处，两份渐渐漂移、自相矛盾。
2. **会话失忆**——每次新会话，代理像失忆一样重新认识项目；收尾时不留交接，下次又从零开始。

这两个坑的本质是同一个：**没有把"规则"和"记忆"工程化**。本文用一次真实的项目治理改动（SCGP 项目），讲清楚三件事：怎么用一份配置覆盖多端、怎么把这份配置写得短而可执行、怎么用「会话启动 / 会话结束」两个文件把会话串成闭环。

---

## 一、一份配置，多端复用：让 CLAUDE.md 退化成指针

最反直觉但最省事的做法：**不要让 CLAUDE.md 承载任何正文**。

`AGENTS.md` 是 Codex 的默认入口，`CLAUDE.md` 是 Claude Code 的默认入口。与其同步两份，不如把 `AGENTS.md` 定为**唯一配置源**，让 `CLAUDE.md` 只写一行引用：

```md
# CLAUDE.md
> 本文件不再单独维护正文。代理配置源统一为 AGENTS.md。
@AGENTS.md
```

`@AGENTS.md` 是 Claude Code 的文件引用语法，会话启动时自动把 `AGENTS.md` 全文加载进来——和直接读 `AGENTS.md` 完全等价。这个方案在 Windows 下比软链接更稳（软链接要管理员权限、git 处理也别扭），且跨平台一致。

> **本次实战**：项目的 `CLAUDE.md` 原本有 12 节正文，和 `AGENTS.md` 大段重叠。改写成 6 行指针后，改规则只需动 `AGENTS.md` 一处，两端自动同步。判断一个项目有没有解决双份维护，看 `CLAUDE.md` 是不是只剩一行 `@` 引用就够了。

## 二、写好 AGENTS.md 的五条铁律

`CLAUDE.md` 退化成指针后，所有重量都压在 `AGENTS.md` 上。它要短、要可执行、要当路由器。

### 1. 越短越好，200 行是硬红线

代理每次会话都加载 `AGENTS.md`，它直接吃上下文窗口。你多写的每一行，都在挤占代理理解代码的空间。

**怎么压**：把"事实"挪走，只留"规则"。项目概述挪给 `README.md`，文档清单挪给 `docs/INDEX.md`，命令全表挪给 `package.json` 的 `scripts`。`AGENTS.md` 里只保留命令的**默认值**（如"类型检查用 `npm run type-check`"），其余一句话指向源头。

> **本次实战**：`AGENTS.md` 从 **426 行压到 126 行**。砍掉的就是导航表（30 行）和命令全表——导航表整段移进 `INDEX.md`，命令只留 5 条最常用的验证入口，其余指向 `package.json`。压完之后代理反而更听话了，因为它不再在海量信息里漏掉真正重要的规则。

### 2. 禁止清单和"要什么"同等重要

只列技术栈不够——代理的知识有截止日，它会"善意"地引入它认为最优、但和你项目历史包袱冲突的依赖。**没有禁止清单的 AGENTS.md 是危险的。**

```md
**禁止清单（Do NOT introduce，除非任务明确要求）：**
- sqlite3 / better-sqlite3 等原生编译数据库依赖（数据层已锁定 sql.js）
- sharp 等原生图像依赖；任何破坏"零额外原生依赖"的运行时依赖
- 新状态管理库（项目已用 Pinia）
- 把未完成的目标态当现状去改
```

这条规则值千金——它防止的不是一次纠正，而是代理在你看不见时埋下不兼容依赖，让后续十次会话都在修兼容性。

### 3. 规则必须可操作，5 秒能判定

"写干净的代码""保持简洁"对代理等于没说。它不懂"干净"，它懂"`<script setup lang="ts">`""路径用 `@/`""单个组件不超过 200 行"。

测试一条规则合不合格：**读完它，你能不能在 5 秒内判断一段代码是否符合？** 能，合格；不能，改写成具体指令。

### 4. 指针而非图书馆

顶级项目的 `AGENTS.md` 是 router，不是 encyclopedia。它不存知识，它告诉代理**去哪找知识**。

```
| 需求           | 读这个              |
|----------------|---------------------|
| 项目概述       | README.md           |
| 文档导航       | docs/INDEX.md       |
| 技术规范       | 重构实施技术规范.md  |
| 当前需求       | docs/planning/...   |
```

这条导航表放在 `docs/INDEX.md`，`AGENTS.md` 里只留一句"按需深读清单见 `docs/INDEX.md`，不要在会话开头一次性全读"。

### 5. 冲突裁定只留一条优先级

文档之间会冲突，必须有一条铁律。写一条、只写一条，且和实际一致：

> 当前代码 > `.continue-here.md` > `AGENTS.md` > `docs/INDEX.md` > 其他文档。

核心是**代码现实高于一切文档**——文档写"已完成"但代码是过渡态，以代码为准，并回头修文档。

## 三、会话启动与会话结束：闭环交接

规则再好，代理还是会忘——因为它每个会话是独立的。解法不是向量数据库，而是两个文件 + 一个联动机制。

### 交接的分层记忆

| 文件 | 职责 | 时间跨度 |
|------|------|----------|
| `.continue-here.md` | 当前唯一下一步（Current State / Next Action / Blockers / Key Decisions / Relevant Files） | 本次→下次 |
| `PROJECT_CONTEXT.md` | 全局背景摘要（架构、技术选型、产品现实） | 跨会话稳定事实 |
| `docs/archive/` | 已完成 / 历史文档归档，不进主索引 | 长期参考 |
| git history | 所有改动的可追溯真相 | 永久 |

这四层加起来，就是可控、可 git 追踪的长期记忆，比任何 MCP 记忆插件都简单。

### 会话结束：五步收尾

1. **全量覆写 `.continue-here.md`**——只留五段结构，`Next Action` 必须小到下次开头能立刻执行（不要把"下一阶段目标"写成下一步）。
2. **条件更新 `PROJECT_CONTEXT.md`**——只有架构 / 技术选型 / 全局约束变了才动；否则明确输出"无需更新"。
3. **Git 分类处理**——禁止 `git add .`，只加精确文件；完整且已验证的才提交；提交 / 推送只在用户明确要求时进行。
4. **自动联动：覆写 `会话启动.md` 的「本次交接」区块**（见下）。
5. **四行摘要**：`Done / Blocker / Next / Repo`。

### 会话启动：四步恢复

1. 按序读 `AGENTS.md → .continue-here.md → PROJECT_CONTEXT.md`。
2. 查 Git 现场（`git stash list` / `git status` / `git log`），**只列 stash 不自动 pop**。
3. 输出固定格式的启动确认摘要。
4. 遇冲突（交接与 Git 状态矛盾、未知 stash、冲突改动）先停，等指令。

### 关键机制：HANDOFF 标记让"结束→启动"自动联动

让「会话结束」自动更新「会话启动」的核心，是一对 HTML 注释标记：

```md
<!-- HANDOFF:START -->
## 本次交接（自动生成，请勿手编）
- 当前任务：...
- 下一步唯一原子动作：...
- 验证命令：...
<!-- HANDOFF:END -->
```

「会话结束」步骤四**只覆写两个标记之间的内容**，保留下方固定流程。这样：

- 覆写位置无歧义，不会误伤流程部分；
- 标记是 HTML 注释，Markdown 预览不显示，但代理能精确定位；
- 下次会话直接粘贴 `会话启动.md`，顶部已是最新交接，读完即开干。

> **本次实战**：执行一次「会话结束」后，`会话启动.md` 第 8–19 行的「本次交接」自动从占位符变成真实内容（当前任务、状态、下一步、验证命令、生成日期）。`.continue-here.md` 是详细源，`会话启动.md` 顶部是可直接粘贴的精简 digest，两处内容要求一致、避免漂移。

### 两个反模糊要求

- **Next Action 必须是原子动作**——"优化性能"不是动作，"把 `foo.ts:42` 的 O(n²) 循环改成 Map 查找"才是。
- **验证命令必须真实**——不要写"自测"，写"`npm run type-check`"。最好列出项目真实的几条验证命令作为默认值，让代理有据可依。

## 四、给规则校准现实：分支规则的教训

值得单独拎出来的一条经验：**规则要匹配实际工作流，否则会被反复绕过。**

最初我按通用最佳实践，在 `AGENTS.md` 里写了"在 main 上提交前先开分支"。但这是个单人项目，历史提交全部直接进 main 并推送。结果规则和实践长期打架——一条总被绕过的规则，比没有规则更糟（它稀释了其他规则的权威性）。

校准后的措辞：

> 本项目单人开发，默认直接提交 main；仅在用户要求或高风险改动（大规模重构 / 合并分支 / 可能破坏主线的实验）时才开分支。

教训：写规则前先看一眼 `git log`，确认它和团队真实工作流一致。

## 总结表

| 原则 | 反直觉点 | 落地做法 | 本次实证 |
|------|----------|----------|----------|
| 单一配置源 | 两份文件同步是负担 | `CLAUDE.md = @AGENTS.md` 指针 | 12 节正文 → 6 行 |
| 越短越好 | 信息多 ≠ 代理更懂 | 事实挪走，只留规则，≤200 行 | AGENTS.md 426→126 行 |
| 禁止清单 | 只说"要什么"不够 | 明确"Do NOT introduce" | 锁定 sql.js / 禁原生依赖 |
| 规则可操作 | "干净"是空话 | 5 秒能判定的具体指令 | `<script setup>`、`@/` 路径 |
| 指针非图书馆 | 不存知识，存"去哪找" | 导航表放 INDEX.md | INDEX.md 成导航中枢 |
| 闭环交接 | 不需要向量库 | 会话结束 ↔ 会话启动 HANDOFF 联动 | 标记自动覆写交接区块 |
| 原子 + 真实验证 | 模糊动作会卡住 | Next 是原子动作，验证是真实命令 | 默认 `npm run type-check` |
| 规则校准现实 | 最佳实践未必适配 | 写前看 git log 对齐工作流 | 分支规则改为默认直接 main |

## 一句话

> 让 `CLAUDE.md` 退化成指针、让 `AGENTS.md` 短而可执行、让「会话结束」自动喂养「会话启动」——把规则和记忆都工程化，代理就从每次失忆的实习生，变成跨会话延续的熟手。
